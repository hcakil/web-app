<a id="production"></a>
# 11. Tell Me About a Difficult Production Problem You Solved

## HERO STORY — Connectivity / Upload Reliability

### Memory route
**Failure → Telemetry → Reproduce → Persistence/retry → Tests/monitoring**

> One example was an upload flow in a production Flutter application. Users sometimes had unreliable mobile connectivity, and if the connection dropped during the request, an upload could fail or leave the user unsure about what happened.
>
> Instead of assuming it was just an API problem, I started with production telemetry and tried to reproduce the unreliable-network path.
>
> We then made the flow more resilient by using local state and connectivity-aware retry behaviour rather than depending on one perfect request. We also added coverage around the failure scenarios.
>
> The important lesson for me was that connectivity is never something a mobile product should treat as guaranteed. Pending, failed and completed states need to be explicit, and the system should recover safely.

## What this story proves
- Production ownership
- User focus
- Debugging
- Reliability
- Evidence over assumption
- Durable fix instead of patch

## If asked for exact metrics
Only give numbers you can defend.

Never invent impact.

3. Show **your decision/action**
4. State **result or lesson**
5. Stop

Target most answers:
- **30–60 sec**
- Hero story: **60–90 sec**

Do not give a 4-minute lecture unless asked.

<a id="hard"></a>
# 🥊 Hard Follow-Ups

Practice these after the normal questions.

### “You say senior. What makes you senior?”
> For me seniority is less about years or knowing more APIs and more about reducing uncertainty for the team. I can clarify the problem, make trade-offs explicit, follow issues across system boundaries, communicate risk, and stay responsible after release.

### “Why should we trust you with a client?”
> Because I'm comfortable working independently without disappearing, I'm transparent about risks and gaps, and I don't treat delivery as finished just because the code is merged. I care about the user outcome and the production result.

### “What if the client wants something you think is technically wrong?”
> I'd first understand the outcome, explain the risk clearly, and give alternatives. I wouldn't turn a technical preference into a veto unless the risk genuinely requires it.

### “What if you don't know a technology the client uses?”
> I separate a real gap from a blocking gap. I wouldn't pretend to have experience I don't have, but if the problem is adjacent to areas I know well and the client is comfortable with ramp-up, I'm confident learning it quickly and transparently.

### “What if priorities change every week?”
> I can adapt to changing priorities. The important thing is making the trade-off visible — what we're stopping, why the priority changed, and what risk that creates.

### “Can you start immediately?”
> I don't want to make a promise I can't keep. I'm still in a transition period, but for a confirmed engagement I can agree on a responsible and concrete start date.

### “Can you lower your rate?”
> I'm open to understanding the client's scope and budget. For senior long-term Flutter work I'd naturally target the upper end of my current range, and then we can see whether the overall fit makes sense.
